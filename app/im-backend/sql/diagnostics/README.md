# 登录异常诊断与账号恢复

修复版本的新密码规则为 6 至 18 位、不能全为空白。
创建用户、管理员重置、用户自行改密共用后端校验。首尾空格会保留，
登录及旧密码校验不套用新规则。初始管理员启动引导仍要求至少 16 位。

## 定位线上账号

1. 核对出问题客户端的实际 API 地址以及服务端部署版本。仓库客户端配置指向
   `https://172.16.59.253:8443`；实际客户端可能有保存的地址，不能仅以仓库值认定。
   管理端生产构建使用同源 API。
2. 通过已有数据库连接，在实际业务库执行 `user_login.sql`，默认检查 `zhangxiaoxia`。
   查询只返回账号状态、时间、用户名编码、密码哈希长度和格式分类。
   `BCRYPT_FORMAT_VALID` 仅表示格式合法，不能证明密码正确或排除重复加密。
3. 发布修复后的后端，让用户自行重试登录一次，在后端日志中按用户名及时间定位
   `Login failed`。记录账号、服务版本和原因，不收集密码、完整哈希或 Token。

| 日志 reason | 处理方式 |
| --- | --- |
| `USER_NOT_FOUND` | 核对客户端地址、业务库和用户名，不自动重建账号。 |
| `ACCOUNT_DISABLED` | 核实禁用原因；状态为空也会拒绝登录，不自动启用。 |
| `INVALID_PASSWORD_HASH` | 密码记录格式或编码器校验异常，由管理员单独重置。 |
| `PASSWORD_MISMATCH` | 确认用户输入与账号无误后，由管理员单独重置。 |

对外仍统一返回 HTTP 401“用户名或密码错误”，具体原因仅在服务端日志中区分。
日志中的用户名会限长并清除换行、控制字符。没有失败日志时应先核对部署版本、
请求是否到达该后端以及 HTTP 响应，不能将网络错误认定为密码不匹配。

## 恢复与发布验收

1. 先发布后端，再发布管理端静态资源；本修复不需要数据库迁移。
2. 只对已确认异常且需要恢复的账号，在管理端“重置密码”设置管理员指定的新密码。
   使用现有 `PUT /api/admin/users/{id}/password/reset`，不要直接在 SQL 中写入密码。
3. 让受影响用户在实际客户端登录；再用至少一个正常账号回归。密码变更后旧密码、
   旧 Token 必须失效，已有 WebSocket 连接必须关闭，新密码应能重新登录。
4. 验证新建用户及用户自行改密可使用 6 位、18 位密码；5 位和 19 位被明确拒绝。
   管理端登录失败显示登录错误，已登录后的接口 401 仍执行过期清理。

保留受影响账号的诊断结论和验收结果。仅通过本地测试或放宽密码长度，不能视为
`zhangxiaoxia` 等线上账号已恢复；没有服务器访问方式时应标注线上核查与发布待完成。
